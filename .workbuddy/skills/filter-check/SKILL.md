# 筛选交互检查（filter-check）

## 我是干什么的

给"筛选"这类功能定一条**合格线**。功能本身写在网站里，我负责回答一个问题：

> **这个筛选，用户用起来会不会卡壳？**

我不管筛选是红是绿、圆是方，只管它该有的出口有没有：没结果的时候是不是一片空白、想撤销的时候能不能一键回到全部。

## 什么时候用我

- 给任何页面新增筛选、搜索、过滤功能（实现前定标准，实现后验收）
- 审查 / 验收一个已有的筛选实现
- 触发词：筛选、搜索、过滤、filter、search、空结果、清空筛选

## 怎么用（三步）

1. **读清单**——先把下面「合格线」八条读一遍，当作实现标准和验收标准。
2. **跑脚本**——在项目根目录执行：

   ```
   python .workbuddy/skills/filter-check/scripts/check_filter.py
   ```

   脚本做**静态扫描**（读 `archive.html`、`app.js`、`style.css`），逐条给"通过 / 未通过"，并打印运行时间和结论。退出码 `0` = 全部通过，`1` = 有未通过项。
3. **逐条核对**——脚本只能查"代码里有没有"，查不了"点下去真的动了没"。所以脚本跑完，还要人工在浏览器里把三种情况过一遍（有结果 / 无结果 / 清空恢复），并把**脚本输出 + 核对结论**留成调用记录。

## 合格线（八条）

| # | 检查项 | 合格的样子 |
|---|--------|-----------|
| 1 | 有结果 | 输入关键字后，页面只剩匹配的卡片，数量与计数一致 |
| 2 | 无结果 | 匹配不到时显示空状态提示（不是一片空白），且提示里给出"清空筛选"的出口 |
| 3 | 清空恢复 | 一键清空后回到全部卡片，输入框和下拉也一起复位 |
| 4 | 结果计数 | 有"找到 N 位角色"这类计数，用户知道筛出了多少 |
| 5 | 关键字容错 | 大小写不敏感（`toLowerCase`）、忽略首尾空格（`trim`） |
| 6 | 不破坏原功能 | 筛选后卡片仍能点进详情页（链接没被筛掉） |
| 7 | 键盘可访问性 | 输入框、下拉、清空按钮都能 Tab 聚焦并操作，控件有 `aria-label` |
| 8 | 视觉一致 | 筛选栏与空状态有专门样式（`.filter-bar` / `#filter-empty`），不裸奔 |

## 固定用法（写筛选时照这套 id / 名字来）

脚本是按这套名字去认的，**改名必须同步改脚本**：

| 用途 | 固定名字 |
|------|---------|
| 关键字输入框 | `id="filter-keyword"`，`type="search"` |
| 职业下拉 | `id="filter-class"` |
| 清空按钮 | `id="filter-reset"` |
| 结果计数 | `id="filter-count"` |
| 空状态容器 | `id="filter-empty"` |
| 筛选函数 | `function applyFilter()`（`app.js`） |
| 筛选栏样式类 | `.filter-bar`（`style.css`） |

## 为什么要把名字固定下来

因为脚本要"认门牌号"。名字统一，脚本才能在不真正打开浏览器的前提下，快速判断代码里筛选该有的部件齐不齐——**这是 Agent 做检查的前提**：先约定接口，再谈自动化。

## 局限（诚实说明）

- 脚本只做**静态扫描**（字符串检查），它证明不了"点下去真的动了"。真正的验收必须靠浏览器实测。
- 脚本认的是名字，不是逻辑。把代码写成空壳也能骗过它——所以脚本是"第一道筛子"，不是全部。
- 只覆盖筛选这一类交互，其他交互（拖拽、弹窗等）不在我职责内。
